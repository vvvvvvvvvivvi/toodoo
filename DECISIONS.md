# Decisions

Log of choices made where the spec was silent, in build order.

## Phase 1 — Scaffold

1. **No react-router.** Bottom-tab navigation is `useUIStore.activeTab` (in-memory state only, no URL routing) — a single-page local-first app has no deep-link requirement.
2. **IDs via `crypto.randomUUID()`** — no `uuid` package.
3. **Drag-reorder via native HTML5 Drag and Drop API** (added in Phase 4) — no DnD library.
4. **Architecture split: dumb Zustand stores + pure `lib/invariants/*` functions + impure `lib/mutations/*` orchestrators.** Stores hold arrays and a `hydrate`/`setAll` setter only. State transitions (added from Phase 2 onward) compute the next state with a pure function, validate it, then write to Dexie and the stores — never commit-then-rollback.
5. **Invariant 1 capacity re-validation** is centralized in one orchestration function (`attemptCapacityMutation`, Phase 2) called by every mutation that can increase planned minutes. `nibbleTask`/direct `shrinkEstimate` are monotonic-decreasing and bypass it.
6. **`isLocked` and clean-plate count are derived, never stored** — keeps the Dexie schema an exact match to the four data-model interfaces in the spec, no extra fields invented.
7. **Circle-ending (Invariant 8) always demotes every incomplete task — locked or not — to `backlog`.** Immediately afterward, in the same synchronous step, `autoPlanDueTasks` (Phase 2/7) re-scans for `deadline <= today` and replants those tasks into whichever circle opens next. This satisfies Invariant 8 literally while producing Invariant 7's observable "requeue same day, or carry to tomorrow" behavior, with no user-visible flash since it happens in one atomic step before any render.
8. **Invariant 10** ("at most one Circle in planning/active state at a time") is enforced globally — there is only one Today screen, so global == per-day in practice.
9. **Fonts self-hosted via `@fontsource/fredoka` + `@fontsource/nunito-sans`** rather than a Google Fonts CDN `<link>` — avoids a runtime network request, consistent with the app's own local-first/no-networking philosophy, while still using the exact typefaces named in the spec.
10. **`fake-indexeddb` added as a devDependency**, imported via `fake-indexeddb/auto` in `src/test/setup.ts`, so Dexie-backed tests run under Vitest/jsdom. Required to fulfill the spec's own "Vitest for every invariant" mandate for invariants that touch persistence.
11. **Tailwind v4 installed (latest), not v3.** Config is CSS-first: design tokens live in an `@theme` block in `src/index.css` rather than a `tailwind.config.ts` JS file (v4 doesn't require one for simple token extension). Using the official `@tailwindcss/vite` plugin instead of the PostCSS pipeline — simpler and is Tailwind's own recommended setup for Vite projects.
12. **`tsconfig.app.json` uses `paths` without `baseUrl`** for the `@/*` alias — TypeScript 6's `moduleResolution: "bundler"` resolves `paths` relative to the tsconfig file without needing `baseUrl`, which is deprecated as of TS 6 and would otherwise throw `TS5101`.
13. **Package manager: npm**, matching the Vite scaffold's own default and simplest fit for a fresh repo with no prior tooling signal.

## Phase 2 — Invariants & mutations layer

14. **`MIN_ESTIMATE_MINUTES = 5`** (`lib/invariants/sizeThresholds.ts`) — the spec doesn't define a floor for "shrink estimate" triage/edit actions; 5 minutes was chosen as the smallest sensible task size, keeping the constant named and in one place so it's easy to revisit.
15. **Split-target tie-break in `getTriageOptions`** (Invariant 4's split suggestion): among unlocked tasks with `remainingMinutes > overflow`, pick the largest; ties break by oldest `createdAt`, then by `id` for full determinism. Not specified by the spec.
16. **`endCircle` always demotes every incomplete task — locked or not — to `backlog`** (implements Phase 1 decision #7). `autoPlanDueTasks` is the system transition that re-plants due tasks into whichever circle opens next, producing Invariant 7's requeue behavior without a 4th task state.
17. **Invariant 9's "filtered to remainingMinutes ≤ gap where possible"** is read as: apply the fit filter, but if it would eliminate every candidate, fall back to the full nearest-deadline/oldest-createdAt sorted list rather than showing an empty tray. This keeps Fill My Day useful even when nothing fits perfectly.
18. **`nibbleTask` and `shrinkEstimateDirect` bypass `attemptCapacityMutation`'s re-validation** (Phase 1 decision #5) since they're monotonic-decreasing and can never cause new overflow — enforced by tests asserting `remainingMinutes` never increases through these paths.
19. **Triage resolution replay:** each `resolve*` action in `triageMutations.ts` re-runs the exact `CapacityMutationRequest` that was originally blocked (stored on `useUIStore`'s triage context) via `attemptCapacityMutation`. If it now commits, the triage sheet closes; if still blocked, `attemptCapacityMutation` re-opens it with the fresh overflow amount itself — so triage is naturally iterative without extra bookkeeping. When triage has no pending request (a proactive locked-only-overflow banner), the resolution just re-checks `validateCircleCapacity` directly.
20. **`resolveGrowStomach` commits directly** without going through `attemptCapacityMutation` — growing the stomach only relieves overflow, never causes it, so no re-validation is needed (same reasoning as decision #18).
21. **`pinToTomorrow` sets the task's `deadline` to tomorrow's local date** and reuses `updateTaskDeadline` — this piggybacks on Invariant 2's existing auto-plan mechanism (`autoPlanDueTasks` picks up any `deadline <= today` backlog task) rather than inventing a separate "pre-planned for tomorrow" concept.
22. **`closeDueCirclesAndReflect` always uses end reason `'closed'`** (never `'cleanPlate'`/`'abandoned'`, which are set elsewhere by `completeTask`/an explicit abandon action) and writes one `DayReflection` per affected calendar date, merging `circleIds` if a reflection for that date already exists (e.g. from an earlier circle closed the same day).

## Phase 3 — Backlog screen

23. **Editing an existing task is scoped to `editBacklogTask`, backlog-state only.** A planned/locked task's estimate changes through the capacity-aware paths (`attemptCapacityMutation` / `shrinkEstimateDirect`) built in Phase 2 instead — those need Invariant 1 re-validation, which a plain backlog edit doesn't.
24. **Backlog list order: newest-first (`createdAt` descending).** Not governed by any invariant (Invariant 9's nearest-deadline ordering only applies to Fill My Day suggestions) — a quick-capture inbox reads naturally with the latest addition on top.
25. **`AppShell`'s root gets a `transform-gpu` class**, establishing a CSS containing block so `fixed`-positioned children (the FAB, the `Sheet` modal backdrop) stay scoped to the centered 480px column instead of the full browser viewport on desktop. Verified via a real bounding-box check in a headless-Chromium pass at 1440px width.
26. **`@testing-library/react`'s auto-cleanup wired explicitly** in `src/test/setup.ts` (`afterEach(() => cleanup())`) — it only self-registers when it detects Jest/Vitest globals, and this project intentionally runs with `globals: false` (Phase 1 decision to keep `describe`/`it`/`expect` explicitly imported rather than ambient).
27. **No drag-reorder or Fill-My-Day integration on the Backlog screen** — those are Today-screen concerns (Phases 4 and 6 respectively); Backlog here is capture/edit/delete only, per spec's screen description.

## Phase 4 — Today screen core

28. **Retroactive Phase 2 fix: Invariant 2 must hold continuously, not just at circle-creation time.** The original `autoPlanDueTasks` only ran inside `createCircle`, so a task captured (or edited to a due-today deadline) *after* a circle was already open would sit unplanted in the backlog until the next circle opened — violating the invariant's literal "a task whose deadline ≤ today is auto-planned" for that whole window. Added `autoPlantIfDueToday` in `taskMutations.ts`, threaded through `addTask`, `editBacklogTask`, and `updateTaskDeadline`, so any of the three ways a backlog task can become due-today re-checks immediately against whatever circle is currently open. Found while building this phase's live demo, not by a test gap — logged here rather than retroactively editing the Phase 2 entry so the discovery context isn't lost.
29. **No backlog-to-circle "add" UI in Phase 4.** The only ways a task enters a circle right now are: due-today auto-planting (decision #28) and directly-seeded test data. Manually moving an arbitrary backlog task into today's Circle is exactly Invariant 1's `addTaskToCircle` capacity-checked mutation (built in Phase 2), which needs the Triage modal to make sense to a user when it blocks — so that UI lands in Phase 5 alongside Feed the Goose and Triage, not here.
30. **Stomach resize control is read-only in the header this phase** — same reasoning as #29: shrinking an active circle's stomach can block via Invariant 1 and needs Phase 5's Triage modal to resolve. The initial size is still fully choosable up front, via `EmptyTodayState`'s preset chips + custom input when first creating the day's circle.
31. **Donut chart is a half-ring (annulus sector) gauge, not pie-slice wedges from a center point** — despite the spec's "wedges" wording, an annulus reads more clearly as a "stomach fullness" gauge and is the standard shape for this kind of half-donut. Rendered as SVG arc paths in `components/today/DonutChart.tsx`; the segment-fraction math is factored into a pure, independently-tested `buildDonutSegments` (`donutMath.ts`) so the geometry logic doesn't need a DOM to verify.
32. **Donut segment ordering: completed (digested) tasks first, by `completedAt`, then planned tasks by `sortIndex`, then one trailing empty segment.** Not specified by the spec; chosen so the visual order roughly matches "what's done" reading left-to-right before "what's left," and locked segments get a 🔒 text glyph at their arc midpoint rather than a nested icon (simpler than sizing/embedding a Lucide `<svg>` inside the donut's own `<svg>`).
33. **The completion/return-to-backlog/nibble buttons call their mutations directly from `TaskRow`** rather than being lifted through prop callbacks all the way to `TodayScreen` — since none of them need cross-component coordination (unlike the drag-reorder state, which genuinely lives in the parent `TaskListToday` because a drop needs to know the full ordered list of siblings).
34. **The "honk shake" on a locked return-to-backlog attempt is CSS-only in this phase** (`.animate-shake` in `index.css`, respecting the global `prefers-reduced-motion` override already in place) — the actual honk *sound* is explicitly bundled into Phase 8 ("sounds/animation, polish pass") per the spec's own build order, not duplicated here.

## Phase 5 — Feed the Goose + Triage modal

35. **`TriageModal` is mounted once, globally, in `AppShell`** (not inside `TodayScreen`) — a blocked mutation can now originate from Backlog's "Add to Today" action too (decision #37), so the overlay needs to be reachable from any tab, matching how `useUIStore.triage` is already a global, not Today-scoped, piece of state.
36. **A visible "that's more than the goose can stomach" banner sits inline on the Today screen whenever `validateCircleCapacity` fails** (tap to open Triage), in addition to Triage auto-opening on a blocked mutation attempt. This surfaces the case introduced in Phase 4 where `autoPlantIfDueToday`/`autoPlanDueTasks` push a circle over capacity as a pure side effect of a due task appearing, with no user action to catch the block-and-open path. Deliberately **not** auto-opening the modal itself on every render though — that would fight a user who intentionally dismissed it (via the sheet's ✕/backdrop) to deal with it later; the banner is the persistent, non-modal reminder instead.
37. **Backlog gained an "Add to Today" action** (`CalendarPlus` icon, shown per-row only while a circle is open), completing the deferred item from Phase 4 decision #29 — it calls `attemptCapacityMutation({ kind: 'addTaskToCircle', ... })` directly, so a blocked add opens Triage exactly like every other capacity-checked mutation, with no separate code path.
38. **The stomach-resize control in the Today header is a click-to-edit inline field** (tap the "{n}m stomach" text to reveal a number input), routed through `attemptCapacityMutation({ kind: 'shrinkStomach', ... })` for both directions (growing trivially passes validation; shrinking below what's already planned opens Triage) — completing the other deferred item from Phase 4 decision #30.
39. **Triage action defaults are computed, not left blank:** the split button pre-fills the exact suggested overflow split; the shrink input defaults to the new-estimate value that would fully cover the overflow (clamped to the task's shrink floor); the move-deadline date input defaults to tomorrow with `min` set to tomorrow, so the picker can't be used to "unlock" into another already-due date. None of these are enforced — a user can still type a different amount — they're just sensible starting points matching the suggestions `getTriageOptions` already computes.
40. **Triage sections render nothing for an empty `targets` array** (except `growStomach`, which has no per-task targets by design) — so e.g. if there's no valid split candidate, the "Split a task" heading simply doesn't appear rather than showing an empty section. Verified via the RTL triage-ordering test asserting the exact heading list for a given scenario.

## Phase 6 — Fill My Day + Poo Pile

41. **`fillMyDayDismissedDate` added to `SettingsRecord`**, not one of the spec's four core data-model interfaces — Invariant 9 requires per-day dismissal to survive a reload (a local-first app persists everything), and there's no natural home for a single date string among Task/Circle/Poo/DayReflection. Reusing the existing settings singleton was the least invasive option, consistent with Phase 1 decision #6's "no extra fields on the core four" — this field lives on the app's own `SettingsRecord`, which was already an addition beyond the spec's literal four interfaces.
42. **Added `lib/mutations/settingsMutations.ts`** (`updateSettings`, `dismissFillMyDay`) — the first write-through mutation for the settings table. `useSettingsStore.update()` itself stayed in-memory-only per its original Phase 1 design; this new module is what actually persists to Dexie, following the same pattern as every other mutations file. Phase 8's Settings screen (day-end time, default stomach, notifications) will reuse `updateSettings` directly rather than inventing its own persistence path.
43. **Fill My Day's "never empty just because nothing fits" fallback (Invariant 9, decided back in Phase 2) is exercised for real here for the first time** — no behavior change, just noting it's now reachable through the UI.
44. **"Another helping?" is triggered by `circles.some(c => c.date === today)`** on the empty-circle path — i.e. any circle at all existed for today already (cleanPlate, abandoned, or closed), not specifically a cleanPlate one. A day that ended in an abandoned circle still deserves "another helping?" rather than being treated as a fresh first-run, since the user has already been through the flow once today.
45. **Poo Pile's per-day breakdown filters by the *local* calendar day the poo's `earnedAt` timestamp falls on** (`poosEarnedOn` in `components/poopile/pooStats.ts`), converting the stored UTC ISO datetime via `Date` getters rather than string-slicing the ISO value — a naive slice would misattribute poos earned late at night to the wrong day for any timezone west of UTC (Invariant 12).
46. **No separate "food size" vs "poo size" vocabulary shown to the user on Poo Pile** — the breakdown just reads Small/Medium/Large, matching `PooSize` directly, since that's the size name a poo actually carries (Invariant 6), not the Snack/Meal/Feast food-size vocabulary used pre-completion.

## Phase 7 — Day-end handling, reflection sheet, notifications, Settings

47. **The fed-vs-digested reflection summary is computed and captured at the moment of closure, held only in `useUIStore` (ephemeral), never persisted.** `endCircle` clears `circleId` off every released task (Invariant 8), so by the time anything downstream could compute "which tasks came from this circle," that link is already gone. Capturing `digestedTaskIds`/`pantryTaskIds` inside `closeDueCirclesAndReflect` — before the clear — is the only point where the association still exists. This was also the reason `DayReflection` itself wasn't extended with summary fields: its shape (`date`, `mood`, `circleIds`) is one of the spec's four core interfaces, and Phase 1 decision #6 committed to no invented fields there. `SettingsRecord` (Phase 6 decision #41) was fair game because it's already an app-only addition; `DayReflection` is not, so the summary stays UI-only and gets recomputed fresh every time closure actually runs — same-session, or on a catch-up reopen days later.
48. **`useDayEndCheck` gates its effect body with an `enabled` boolean parameter rather than being called conditionally** — React hooks can't be called after an early return (`App.tsx`'s boot-loading gate returns before rendering `AppShell`), so the hook is always called at the top of `App`, and `enabled={!booting}` controls whether its internal check actually runs. This avoids running the day-end catch-up against empty, unhydrated stores on the very first tick.
49. **No "already notified" guard needed in `useDayEndCheck`** — `closeDueCirclesAndReflect` only returns a non-empty summary array on the tick where it actually closes something; once closed, `getCirclesNeedingClosure` naturally excludes it from every later check (its state is no longer `planning`/`active`). So gating the `Notification` call on "summaries.length > 0" already prevents repeat notifications for the same closure, without extra bookkeeping — and still fires again correctly for a second same-day circle (Invariant 10) that later crosses its own day-end.
50. **Notification permission is requested manually via the Settings toggle in this phase**, not automatically after the first successful Feed the Goose — that auto-prompt is explicitly a First-run-flow behavior per the spec's own build order ("8. First-run flow... "), and First-run hasn't been built yet. Toggling on calls `Notification.requestPermission()` directly and stores whether it was actually granted; toggling off just clears our own flag (the browser permission itself can't be programmatically revoked).
51. **`EmptyTodayState` now seeds its initial minutes from `settings.defaultStomachMinutes`** instead of a hardcoded 480 — this was a latent gap since Phase 4 (the Settings screen didn't exist yet to make it visible). Fixed here since Settings' "default stomach hours" control would otherwise silently do nothing.
52. **The reflection sheet's mood picker always targets `localToday()`, not the date(s) actually being closed.** If a catch-up sweep closes several stale circles from different past dates in one pass (a long-idle reopen), there's still only one 3-emoji picker shown, and it's simplest/most honest for it to represent how the user feels *right now, reflecting*, rather than trying to disambiguate moods across several different closed-out days.

## Phase 8 — First-run, notification auto-prompt, sound/animation polish

53. **`firstRunComplete` added to `SettingsRecord`** (same reasoning as `fillMyDayDismissedDate`, decision #41) — the intro cards must show exactly once ever, which means the flag has to survive a reload. The field that used to live on `useUIStore` (ephemeral, reset to `false` on every boot — a latent bug, since it meant the cards would in fact have reshown on every single page load) was removed entirely in favor of reading `settings.firstRunComplete` directly; there is now exactly one source of truth for this flag instead of two that could disagree.
54. **`requestNotificationPermission` extracted as a shared helper in `settingsMutations.ts`**, used by both the Settings toggle (Phase 7) and the first-run auto-prompt (this phase) — it never re-prompts once the browser has already denied permission, and enables our flag immediately (without re-prompting) if permission was already granted some other way. Centralizing this avoids the two call sites drifting out of sync on that "don't re-prompt" rule.
55. **The auto-prompt fires from inside `feedTheGoose` itself**, gated on `!circles.some(c => c.savedAt)` checked *before* the mutation commits — i.e. "no circle has ever been successfully saved before this one." This is the precise reading of "only after the first successful Feed the Goose, never on load": a blocked save (triage opens instead) does not count, and it never fires again for the second, third, etc. successful save.
56. **The intro copy is split one sentence per card** ("Tasks are food." / "I eat what fits." / "I poo when it's done.") rather than showing the full tagline on every card — matches "3 static intro cards max" from the spec, and completing the last card calls `completeFirstRun()` then explicitly sets `activeTab` to `'backlog'`, landing the user in the empty Backlog exactly as specified, rather than wherever `activeTab` happened to default to.
57. **The honk sound is a programmatically generated short WAV** (~220ms descending sawtooth tone, `lib/audio/honk.ts`), not a sourced/licensed audio asset — the spec explicitly allows "short base64 audio ok" for a placeholder, and generating it avoids any asset-licensing question for a sound that's expected to be replaced with real sound design later.
58. **`playHonk()` swallows every failure mode defensively** (missing `Audio` global, `play()` returning `undefined`, a rejected autoplay promise, or a synchronous throw) rather than propagating any of them — sound is a nice-to-have UI cue, and JSDOM's test environment doesn't implement `HTMLMediaElement.play()` at all, so this also keeps the test suite honest without special-casing test environments in product code.
59. **The completion micro-animation delays the actual `completeTask` call by 200ms** (`TaskRow`'s `COMPLETE_PULSE_MS`) rather than animating a task that's already gone — since completing a task immediately removes its row from the planned-tasks list (it's filtered by `state === 'planned'`), there'd be nothing left on screen to animate without this short, deliberate hold. The complete button disables itself for that window to prevent a double-fire (and a duplicate poo).
60. **No separate "reduced motion" branch for the honk sound** — `prefers-reduced-motion` is a motion preference, not an audio one; the existing global CSS rule already collapses the pulse animation to instant when set, and the sound plays independently either way.

## Post-MVP redesign — single page, full-circle donut, visual-first pass

Requested directly by the user after using the finished MVP: fewer words, more visuals, one page instead of four tabs, and a full circle instead of a half-circle gauge. Pure UI/navigation restructuring — none of the 12 invariants or the `lib/invariants/*`/`lib/mutations/*` layer changed.

61. **"The toodoo list" = the existing Today page (donut + today's task list)**, kept as the single main page. Backlog, Poo Pile, and Settings — previously tabs — became modal overlays opened from a top-right icon dock (`components/layout/IconDock.tsx`, icon-only per the user's explicit "icons docked at the top right corner"). `TabBar.tsx` was deleted outright rather than kept dormant.
62. **`useUIStore`'s `activeTab: Tab` / `setActiveTab` replaced with `activeModal: Modal | null` / `openModal` / `closeModal`** — a page-switch model doesn't fit a single-page app; a nullable "which overlay is open" model does, and mirrors the pattern `triage` and `pendingReflection` already used. Decision #56 (Phase 8) — IntroCards setting `activeTab` to `'backlog'` on completion — is now moot: finishing onboarding just reveals the one main page, there's nothing to switch to.
63. **Backlog/Poo Pile/Settings render inside the existing `Sheet` component** (the same bottom-sheet used for Triage, Reflection, Add Task, and Nibble) rather than a new full-screen modal primitive — one modal pattern for the whole app, and it already supports scrollable content up to `85vh`. Their root wrappers' `h-full` centering (written for a full-viewport tab) was swapped for plain padding-based centering (`py-12` etc.), since `h-full` against a Sheet's auto-height content wrapper would collapse to zero.
64. **`AddTaskFab`'s `bottom-20` offset (sized to clear the old bottom tab bar) dropped to `bottom-6`**, and `BacklogList`'s bottom padding shrank from `pb-28` to `pb-20` to match — there's no more bottom bar to clear.
65. **Donut geometry: full 360° sweep starting at 12 o'clock, clockwise** (`angleForFraction = 90 - 360 * fraction` in `DonutChart.tsx`), replacing the half-circle's `180 * (1 - fraction)`. `donutMath.ts`'s segment-building logic and `[0,1]` fraction semantics are untouched — only the angle formula and viewBox/center (now square, `260×260`) changed, keeping the pure segment math and its tests (`donutMath.test.ts`) valid without modification.
66. **A segment spanning ~360° (a single task exactly filling the whole stomach) is split into two 180° arcs before rendering** — SVG can't express a true 360° sweep as one arc command (the start and end points coincide, which renders as invisible in most engines), so `ringSegmentPath` recurses through the midpoint fraction whenever a span exceeds 359.99°.
67. **A goose emoji sits in the now-real center hole of the ring** — the half-circle version had no comparable space; full-circle donuts read as an obvious place for a focal mascot, so it's a `<text>` element rather than a nested `<svg>`/`foreignObject` (same lightweight technique as the existing lock-glyph marker).
68. **Poo Pile's "Small: 2 Medium: 1 Large: 0" text rows replaced with a cluster of 💩 emoji sized per category** (`PooCluster` in `PooPileScreen.tsx`) — the count is seen at a glance rather than read, per the visual-first request. The underlying `pooStats.ts` breakdown data and its tests are unchanged; only the rendering changed.
69. **Today's header dropped the literal "Today" label** — redundant once it's the only page — keeping just the stomach-size control, with right padding (`pr-32`) reserved so it never sits under the fixed icon dock.

## Post-MVP round 2 — remove Feed the Goose, tagging, edit/delete on Today, circle history, Add Task into the dock

70. **`createCircle` now calls `feedTheGoose` immediately after inserting the circle**, instead of leaving it in `planning` for a manual save. `attemptCapacityMutation` already re-validates every capacity-affecting mutation regardless of this button's existence, so removing it removes zero safety — only the "confirm you're done planning" ceremony. On the rare unhappy path (auto-planted overdue tasks alone already overflow the freshly chosen stomach size), the circle stays `planning` and Triage opens automatically at creation time; resolving it replays and activates the circle via the same `pendingRequest` mechanism `attemptCapacityMutation` already had, so no button is ever needed to recover. `FeedTheGooseButton.tsx` was deleted outright.
71. **`Task.tags?: string[]` added with no Dexie index or version bump** — it's a plain stored field, never queried/filtered by, so existing rows without it simply read back as `undefined`; every consumer treats it as `tags ?? []`. Comma-separated free text in `AddTaskSheet`'s new "Tags" field, parsed/trimmed/deduped into an array on submit — no tag-picker/autocomplete UI, kept to the simplest thing that displays as chips (`components/shared/TagChips.tsx`, shared by `BacklogTaskRow` and `TaskRow`).
72. **New `editPlannedTask` mutation for editing a task already on Today**, distinct from `editBacklogTask` (backlog-only). Title/tags/deadline are direct edits (Invariant 2 only restricts delete/return-to-backlog for locked tasks, and Invariant 3 explicitly allows shrinking or moving the deadline of a *locked* task, so editing generally is never restricted by lock state). An estimate change is delta'd through the existing capacity-aware paths — growing goes through `attemptCapacityMutation`'s `growEstimate` (may open Triage), shrinking goes through the existing monotonic `shrinkEstimateDirect` (always safe) — reusing both rather than inventing new capacity logic.
73. **Delete on Today reuses `deleteTask` directly** (already refuses locked tasks) with the same shake-feedback pattern `TaskRow` already had for the locked return-to-backlog refusal, rather than a separate confirmation dialog.
74. **"Pin to tomorrow" wasn't actually broken — it had zero visual feedback.** The click handler and mutation both fired correctly; a successful pin looked identical to a dead button, which reads as "not working." Fixed by giving `PinToTomorrowButton` its own local "pinned" state: label swaps to a disabled "Pinned ✓" once clicked. No underlying wiring bug found — verified live in the browser as well as by test.
75. **Circle history is read from existing data, nothing new persisted.** `getPastCircles`/`getDigestedTasksFor` (`components/history/circleHistory.ts`) are pure derivations over the existing `circles`/`tasks` stores — completed tasks keep their `circleId` forever (only backlog-released tasks lose it, Invariant 8), so "what got digested in this past circle" stays reliable no matter how long ago it closed. A fifth icon-dock entry (`History`, lucide) opens it as a `Sheet`, same pattern as Backlog/Poo Pile/Settings.
76. **Add Task moved off a corner FAB into the icon dock** (`activeModal: 'addTask'`), visually distinguished with the primary/filled color since it's the main CTA versus the neutral color of the other four icons. The "capture, then auto-plant into the open circle if one exists" logic (previously duplicated between `TodayScreen` and `BacklogScreen`) moved up to `AppShell`, since it's now reachable from anywhere rather than tied to whichever screen happened to render the FAB. `BacklogScreen` lost its own add flow entirely — it's edit/delete/add-to-today only now, since capture happens exclusively through the dock. `components/shared/AddTaskFab.tsx` was deleted.
77. **Icon dock is now 5 icons (Add Task, Backlog, History, Poo Pile, Settings)**; `TodayScreen`'s header clearance bumped from `pr-32` to `pr-40` to keep the stomach-size control clear of the wider dock — verified visually rather than computed precisely, since the header only ever holds that one short control.
